# Deploy

How the zeroroot platform is provisioned, brought up, torn down, and promoted across environments. This context owns the **infra plane** (Terraform: the AWS accounts, the EC2 instance for staging and for drill, the EKS cluster for prod) and the **bringup/teardown mechanics**. The GitOps app plane lives in `gitops/` of this repo.

## Language

**Environment**:
One of the named targets of this repo: **staging**, **drill** and **prod**. Staging is permanent and is the first stop of a promotion. Drill is the throwaway copy for destroy, recreate and restore tests (ADR-0095). `kind` is a cluster type for CI and a workstation, not an Environment. Staging and drill are each **one EC2 instance that runs k3s** (`bootstrap/ec2/gibson`). Prod is an EKS cluster (`bootstrap/eks/gibson`). The three **co-tenant the single `000000000000` ("Zero Root AI") workload account**. Each has its own VPC, its own cluster and its own durable bucket. No secret name prefix separates them: each cluster holds its secrets in its own OpenBao. Postgres runs in the cluster, from the chart. The org management account is `111111111111`, the parent holding organization, and hosts no workloads. See ADR-0073.
_Avoid_: stage, environment-tier, "the cluster" (name the env)
_Exception_ [2026-08-18 Q3=A]: the `eks/public-site` root has **no Environment**. The public web surfaces are production-only singletons; there is no staging marketing site. Every other root in this repo is env-forked — do not "fix" this one by adding `envs/`.

**Infra plane**:
The Terraform-provisioned layer Argo cannot manage because Argo depends on it. Decided 2026-09-01 ([ADR-0083]), built in deploy#1744: it splits into stage 0, the **substrate bootstrap**, which outlives clusters, and stage 1, the **cluster**, a thin per-cloud module (EKS, EC2 with k3s, kind) that both teardown modes destroy. KMS, Secrets Manager, Aurora, SES, WAF and GuardDuty left the infra plane: the chart carries their portable equivalents (OpenBao with the `static` seal, CNPG, the SMTP relay, Coraza). `scripts/check-stage1-shape.py` keeps every stage 1 root under the block ceiling and free of the deleted classes, and refuses a root in the tree that its list does not name. There are two roots since 2026-09-22 (ADR-0095, hosted#159): `bootstrap/eks/gibson` for production, and `bootstrap/ec2/gibson` for an environment on a plain cluster, which is one EC2 instance running k3s. Staging runs there. Stage 0 and stage 2 are shared, and so is everything in a recreate that is not the cluster itself (`scripts/lib/bringup-before-cluster.sh`, `scripts/lib/bringup-after-cluster.sh`). Blocker 1's exit test plans the root the selected environment builds, from that environment's own state, and `scripts/check-blocker1-root.py` holds the two to the same pairing the Makefile's recreate rows use.
_Avoid_: "the terraform", phase 0 (Phase 0 is a narrower pre-Argo in-cluster step)

**App plane**:
Everything Argo syncs from the gitops `apps/` tree once the infra plane and the root Application exist.
_Avoid_: workloads layer

**Promotion**:
The one-way movement of a **released chart version** through the environments: a one-line PR on gitops `main` that bumps the OCI `targetRevision` in `envs/staging`, then the same version in `envs/prod` (ADR-0072). No branch per environment. Rollback is pinning the previous version.
_Amended 2026-08-25 (grill Q1=A)_: this entry previously said "a PR merge between the gitops branches dev→staging→prod", which ADR-0072 replaced; the code has had per-env overlay directories on one `main` since then.
_Avoid_: deploy-to-prod, push, "merge to staging" (there is no staging branch; the staging event is the version bump)

**Prod promotion** [grill 2026-08-25 Q6=B]:
Automatic on staging green: when the staging smoke passes for a version, the `envs/prod` bump for that same version opens and merges itself. `make check-promotion-pr` stays the guard — it refuses any version staging has not pinned first, so a green smoke is the only path to prod and a mismatch is blocked. No human between a green staging and customers; the human decision is the merge of the PR (see **Done**).
_Avoid_: "prod button" (there is none), promoting a version staging did not run

**Staging is permanent** [ADR-0095, replaces "Staging on demand" of 2026-08-25]:
Staging stays up. It is one EC2 instance with k3s. No workflow tears it down or rebuilds it, and `scripts/check-staging-not-ephemeral.py` holds that. One dispatch, `promote-staging`, syncs the bumped chart version to the running cluster through `make with-cluster`, runs the smoke and reports on the release. Each destroy, recreate and restore test runs on **drill**. An operator rebuilds staging from a workstation, after the serverName pull request, and only for a change that needs a new node. A staging failure opens one issue per failure, after the merge, never before it.
_Avoid_: "staging is down so we cannot ship" (the merge ships; staging proves), staging on demand, a teardown of staging as a test

**Dev cluster** [grill 2026-08-25 Q8=B′]:
The workstation held one kind cluster as the dev Environment. That cluster, its overlay `gitops/envs/dev` and its lock targets are deleted (ADR-0095, hosted#406). No step of **Done** needs a cluster.
_Avoid_: "my kind cluster" per agent, a cluster run as a condition of a merge

**Merge gate** [grill 2026-08-25 Q2=A]:
The set of checks a PR must pass before it merges, and its budget: the required aggregator finishes in **10 minutes** or the slow job leaves the set. In the set: formatting, lint, unit tests, the render guards (bats and the chart guards), the secret, RBAC and image-registry guards, CodeQL, govulncheck. Out of the set, running on push to `main` and on the daily schedule only, never on `pull_request`: every exit test, the baseline install, the Docker edge harness. They are not part of the merge.
_Avoid_: "CI green" meaning every workflow (only the gate blocks), running a cluster on a PR

**Done** [owner decision 2026-10-05, ADR-0080]:
A change is done when its PR merges with every required check of the **merge gate** green, and the body closes the issue with `Closes #N`. No manual run on a cluster and no local sign-off target is part of done. The agent merges through the merge queue when the **merge gate** is green. The PR body carries `Closes #N` for an issue in the same repo, or the full issue URL for an issue in another repo, because GitHub ignores the `Closes repo#N` form. The merge is the release event: release-please cuts the version, the umbrella publishes, and the `envs/staging` bump follows automatically. Nothing downstream blocks it. A staging failure opens its own issue, one for each failure.
_Avoid_: "sign-off merge", "dev sign-off" (both retired 2026-10-05), "done when the exit test passes" (the exit tests run on `main` and do not gate the merge), "merge to staging"

**Full-ephemeral teardown**:
The teardown profile of stage 1 in each environment: `make teardown ENV=<env> MODE=wipe|preserve` destroys **everything** that stage 1 built, the cluster and each volume in it, to ~$0 idle spend. Stage 0 survives: the durable bucket, the DNS sub-zone, the SMTP relay and the keyring. A recreate restores customer-critical state from a named backup in the durable bucket. Drill is torn down after each run. Staging is not torn down as a routine (ADR-0095). Contrast the rejected **data-preserving teardown**, which kept resources of stage 1 and attached them again (see ADR-0083).
_Avoid_: nightly teardown (that's a cadence, not the profile), reset

**Recreate**:
Standing an environment back up from nothing: cluster (infra plane) → Argo sync (app plane) → **restore-on-bringup** only when a backup is **named** → smoke. A recreate **never restores unless told which backup, by name** ([ADR-0083]). Without a name every store bootstraps empty, always, even if the durable bucket holds a hundred backups. A **wipe teardown** followed by a recreate must come up empty, and auto-detecting "latest" would silently resurrect what the wipe removed.
_Avoid_: redeploy, rebuild, restore (that is the optional step inside it)

**Restore-on-bringup**:
The step that repopulates customer-critical stores from the **durable bucket** during a recreate. Paired with a **backup-before-teardown** step. Decided 2026-09-01 (grill): the mechanism is a **Velero backup** for Kubernetes objects and volume data, with each store's own export where it has one. Net-new work as of [ADR-0083].
_Avoid_: seed, migration

**Durable bucket**:
The one S3-compatible object store that outlives every cluster. It holds Terraform state under `tfstate/` and every backup artifact under `backups/`. It is the only thing a destroy is not allowed to touch, and the only external dependency the substrate contract adds to "a Kubernetes cluster". S3-compatible so it is the same on AWS, GCS, R2, MinIO, or a customer's own store. Decided 2026-09-01: the **substrate bootstrap** creates it on the clouds we run ourselves, and an operator may bring an existing one on-prem. Either way **preflight** proves the same three properties: versioning on, the platform credential cannot delete objects, a lifecycle rule owns retention. The one carve-out is `s3:DeleteObject` under `backups/velero/`: kopia removes its own session markers on every flush and a repository that cannot do that completes no backup. It is never `s3:DeleteObjectVersion`, and the bucket is versioned, so that delete writes a delete marker and the version stays until the lifecycle rule expires it. The guarantee lives in preflight, not in who created the bucket.
_Avoid_: backups bucket (that is one bucket among five today), state bucket, the cloud

**Apex zone**:
The `zeroroot.ai` hosted zone and every record on it that is company property rather than environment property: the Google Workspace MX, SPF, DKIM and DMARC records, the SES domain identity and its DKIM CNAMEs. **Permanent.** It is owned by an org-level workspace that has no teardown target, never by an environment, and no teardown mode may touch it. Today the prod estate creates it (`route53_zone_name = "zeroroot.ai"`, held only by `prevent_destroy`), which is the retain model being deleted, so the zone moves out of `eks/gibson`. Environments get delegated sub-zones (`staging.zeroroot.ai`) from their **substrate bootstrap**. Application records (`app.`, `api.`, `www.`) are written by external-dns under its ownership TXT and are the only records an environment may create or delete in the apex. **Preflight** proves the mail records are present before stage 1 starts.
_Avoid_: the zone (name which one), prod zone, root zone

**Substrate bootstrap**:
Stage 0 of a bringup, applied once per **environment**, and the only stage allowed to differ per cloud. It provides the things that outlive every cluster: the **durable bucket**, the DNS zone, an SMTP relay endpoint, the **bringup keyring**, and the registry of the signed setec sandbox disks (D85). It ends by writing `substrate.env`, the one artifact stage 1 is allowed to read. On AWS it is `eks/gibson-bootstrap` (`make substrate ENV=staging|prod`, deploy#1742): one durable bucket `zeroroot-ai-<env>-durable-<account>` with SSE-S3 and S3 native state locking, no KMS key and no lock table, the platform and SMTP credentials, the sub-zone and its NS delegation. Its own state is local, under `SUBSTRATE_DIR/<env>/` next to the keyring. On AWS the disk registry is one private ECR repository per environment, and on kind a local registry container (`SETEC_DISK_REPO` in `substrate.env`). kind satisfies it with MinIO and a local zone, so the same gate runs daily on a workstation. kind has no SMTP relay: the chart's in-cluster Mailpit sink carries its mail (hosted#126).
_Avoid_: bootstrap (ambiguous with the self-hosted first-admin seed), phase 0, prerequisites doc

**Cluster (stage 1)**:
The thin per-cloud layer between the **substrate bootstrap** and the umbrella chart. Decided 2026-09-01 ([ADR-0083]): it provides exactly six things and nothing else. Storage (a CSI driver and a default `StorageClass`), a `LoadBalancer` implementation, node autoscaling, metrics-server, the sandbox runtime (`/dev/kvm` on each fleet node, for the setec launcher pod, per [ADR-0083]), and Argo CD. The per-cloud difference is which implementation fills each row, never whether the row exists: EBS CSI, the AWS LB controller and Karpenter on EKS. local-path, the kind cloud-provider and nothing on kind. Everything else that used to be a pre-Argo `helm_release` (External Secrets, cert-manager, external-dns, CNPG, the observability agent) is a platform concern and lives in the umbrella as a subchart ordered by sync-wave. Deleted: the AWS Private CA issuer and Argo Image Updater. Both teardown modes destroy the whole stage. Documented with diagrams in `docs/bringup.md`.
_Avoid_: bootstrap-addons (the Terraform module being deleted), phase-0 operators (the kind name for the same drift), infra plane (the old undivided layer)

**Preflight**:
The gate between stage 0 and stage 1. `make preflight` reads only `substrate.env` and proves each line live: write and read back an object in the durable bucket and check its three properties, check each keyring member by length and fingerprint, open a TCP and `AUTH` session to the SMTP relay, resolve the zone's NS records, and on an AWS environment ask the apex zone's own nameserver for its MX, SPF and DKIM records. It prints a checklist and exits non-zero on the first miss. `make recreate` depends on it and nothing else can start stage 1. A preflight that passes with a missing input is a defect in preflight.
_Avoid_: smoke (that runs after bringup), sanity check, validate

**SMTP relay**:
The only mail interface the platform has. Every sender (gibson, Zitadel, Alertmanager) takes a host, port and credential from the **bringup keyring**. Which relay stands behind it is a substrate choice: SES through its SMTP endpoint on AWS, an enclave's own Exchange or Postfix in an air gap. kind has no relay: the daemon's client sends no credential in clear text to a host other than localhost, so a kind relay without trusted TLS was unusable. The chart's in-cluster Mailpit sink, with no AUTH, is the kind mail path (hosted#126). Deliverability records (DKIM, SPF, DMARC, mail-from MX) belong to the relay owner and live on the **apex zone**, never in the chart and never in an environment. The platform runs no mail transfer agent: SMTP is a substrate input, like DNS.
_Avoid_: SES (one relay among several), email provider, mailer

**Velero backup**:
A backup of the runtime Kubernetes objects that are not in git and of volume data, written to the durable bucket. Decided 2026-09-01: **include by default, exclude desired state by label.** It covers every `tenant-*` namespace and the `gibson` namespace whole. The label is Velero's own `velero.io/exclude-from-backup: "true"` (implemented 2026-09-01, deploy#1735: the item collector enforces that label itself, and a custom label would have needed a second mechanism to mean anything). The chart puts it on the `PlatformBootstrap`, on the CNPG `Cluster`, and, through the Cluster's `inheritedMetadata`, on the pods and PVCs the CNPG operator derives from it, so no file-system copy of a Postgres volume ever restores over a `bootstrap.recovery`. The `OIDCClient` children are created by the platform-operator with no label yet: they ride in the backup and a restore conflicts loudly with the operator-recreated copy, which is the safe direction. A missed exclude shows as a loud restore conflict, never as lost data, which is why the allowlist shapes were rejected. The `Tenant` CR is cluster-scoped, so the backup spec names `tenants.gibson.zeroroot.ai` in `includedClusterScopedResources` — a namespace-shaped backup carries a cluster-scoped kind only when it is named. **It never contains a Secret.** Velero's cluster role names no `secrets`, in any verb, and it holds no cluster-admin binding (the cluster-admin binding is why deploy#1193 removed it). Velero runs as its own release, `helm/gibson-velero`, in the `velero` namespace: the server reads its kopia repository password through a cache restricted to its own namespace, so whichever namespace it runs in is a namespace where it can read every Secret. That namespace holds two objects, both Velero's own. Secrets live in the secret store only, and come back on recreate through External Secrets, so the restore order is secret store → ESO → Velero restore. One pre-backup hook rides with it: Neo4j runs `CALL db.checkpoint()` (pod exec, `onError: Fail`) on the tenant pods and the platform graph pod, so the file-system copy carries a fresh checkpoint and a failed or timed-out checkpoint makes the backup fail instead of Completed. Measured 2026-09-02: `db.checkpoint()` is an Enterprise procedure and the pinned `neo4j:5.26.0-community` does not register it, so on that image the hook falls back to `CALL db.ping()` when and only when the error is the procedure's absence — the store must still answer, community recovers through its periodic checkpoint (15 minutes) plus transaction-log replay, and every other error still fails the backup. The ESO generator kinds (`generators.external-secrets.io`) get the secrets treatment, because a Fake generator and a GeneratorState can carry literal secret material: no RBAC verb, and the backup spec excludes the group by glob. The Postgres coordination is NOT a Velero hook (implementation finding, deploy#1735): Velero's only hook mechanism is an exec inside a target pod, and "create a CNPG `Backup` and wait for `completed`" is an API step. It is the script step `test/dr/cnpg-backup-and-wait.sh`, which the **preserve teardown** runs before its Velero backup and whose timeout fails the whole teardown. The hourly Schedule does not run it, because the CNPG WAL archive already gives Postgres a five minute recovery point. The operator adopts a restored Neo4j PVC rather than re-initializing it (`dataplane/neo4j.go`, idempotent create), so built-ins restore first and the tenant CRs after.
_Avoid_: snapshot (a CSI snapshot is cloud-specific and is not what this is), full backup, cluster backup, backup allowlist

**Secret store**:
OpenBao, and only OpenBao, on every substrate (decided 2026-09-01, extends the 2026-08-20 option D call from self-hosted to kind and EKS). It is the one External Secrets backend, reached through one `ClusterSecretStore` over OpenBao's kubernetes auth mount, role `eso-reader`, with ESO's own ServiceAccount and no stored credential. The `auth/jwt` mount stays what it is: the SPIFFE JWT-SVID validator, which a plain ServiceAccount token is not. Its **seal** is the OpenBao `static` seal, keyed from the **bringup keyring** by `file://`, on every substrate. Its **seed** is the `openbao-auto-init` sidecar, which writes every key in `helm/gibson-workloads/files/openbao-seed-keys.txt` (24 today) while it holds the initial root in memory, and then revokes it. On every later start it logs in with the `openbao-seeder` role, bound to its own ServiceAccount, and reconciles the same table. The two inputs that are not self-generated (the GHCR pull token, the LLM keys) arrive through the keyring members GHCR_PULL_TOKEN and LLM_KEYS_JSON. Deleted with this decision: the `global.secretBackend: aws | kind` knob and its validator, the `kubernetes` and `kms` seal branches and their unseal-key Secret, `kind/gibson/credentials.tf`, and `eks/gibson/modules/secretsmanager`. A restored store auto-unseals at recreate by design, so the drill's assertion becomes "without the keyring the archive cannot be opened", and **backup-verify** proves the positive half before every destroy.
_Avoid_: vault (the product is OpenBao), Secrets Manager, secretBackend, the ESO backend (there is one, name it), unseal keys (the static seal has one key, a keyring member)

**Bringup keyring**:
The small set of keys without which nothing in the durable bucket is readable: the OpenBao `static` seal key and the Velero repository password. It lives in **GitHub Environment secrets**, which is the main driver of change and always retains a copy, and it **may also live on the laptop of a developer who is allowed to hold it**, so a recreate can run outside GitHub. It never lives in a cluster, in the bucket, or in OpenBao. Rotation re-wraps, never re-encrypts data. Decided 2026-09-01: no human in the loop at restore; the automation that runs a recreate holds the keyring.
_Avoid_: root key, master key (that is a transit key inside OpenBao), unseal key (one member of the keyring, not the set), the orchestrator's secret

**Bringup verbs**:
The whole operating surface for an environment: `preflight`, `teardown`, `recreate`. Each is one make target and one GitHub workflow with the same name and inputs, and there is no other path (decided 2026-09-01, [ADR-0083]). `teardown` takes `MODE=wipe|preserve` with **no default**, so nobody gets the destructive mode by omission. `recreate` restores only when `RESTORE_FROM=<name>` is given ([ADR-0083]). **Staging** runs any verb from a laptop that holds the **bringup keyring** or from the workflow, with no approval. **Prod** runs `teardown` and `recreate` only through the workflow, and the `prod` GitHub Environment protection rule requires one named reviewer to approve the run. That is the one human step in the design, and it guards destroying prod, not restoring it. An agent runs any verb on staging directly. On prod it triggers the workflow, reports the run URL, and a person approves. `eks-up`, `eks-down` and `eks-reset` are deleted, not aliased. A restore of staging or prod opens a PR that writes the new Postgres archive name into the overlay. After it merges, `make restore-settle ENV=<env>` removes the three recovery parameters from the live gibson Application, so Git is the truth again (D91).
_Avoid_: eks-up / eks-down / eks-reset (deleted), standup, nuke, "the workflow" (name which verb)

**Wipe teardown**:
Destroy the cluster and everything in it, keep nothing. It deletes nothing from the durable bucket (retention prunes old backups on its own schedule) and the next recreate does not consult the bucket. One of the two teardown modes an operator, or an agent acting for one, can ask for.
_Avoid_: reset, nuke

**Preserve teardown**:
Backup-before-teardown, **backup-verify**, then destroy. A backup that cannot be proven readable **aborts the teardown and leaves the estate standing**, with no automatic fallback to a wipe teardown. An agent told to preserve reports the abort and the failing check, and does not wipe on its own. The other teardown mode. It ends by printing the backup name a later recreate must carry ([ADR-0083]).
_Avoid_: safe teardown, graceful teardown, data-preserving teardown (the rejected retain-and-reimport model)

**Backup cadence**:
The recovery point objective for unplanned loss, stated per store and met by a schedule, not by teardown (decided 2026-09-01). Postgres: **5 minutes**, CNPG continuous WAL archive with `archive_timeout: 300s` and one base backup a day. Neo4j graphs, OpenBao and the tenant CRs: **1 hour**, one Velero `Schedule` with the checkpoint hook. Retention lives in the **durable bucket**'s lifecycle rules and nowhere else: `backups/` 30 days hot then expired at 180, `audit/` 6 years with object lock, `tfstate/` versioned and never expired. **Preflight** proves those three rules exist. The backup a **preserve teardown** names is tagged so retention does not prune it until the next successful recreate. **Prod is never routinely torn down**: a prod preserve teardown exists for a planned dark period or disaster recovery only, and needs the reviewer approval. Staging stays up (ADR-0095). Drill is torn down after each run.
_Avoid_: backup schedule (name the RPO, the cron follows), snapshot interval, retention policy in the chart (there is none, the bucket owns it)

**Backup-verify**:
The gate inside a **preserve teardown**, run after the backup and before the destroy, using the exact **bringup keyring** the automation will hold at recreate. Decided 2026-09-01: it is a **canary decrypt**, not a manifest check and not a full restore. It opens the Velero repository with the repository password and restores one canary object into a scratch namespace, lists the CNPG backup catalog and checks WAL archive continuity, and decrypts a ciphertext recorded before the backup with the OpenBao seal key. Under two minutes. A manifest check alone (phase `Completed`, sizes non-zero) proves an upload happened and nothing about readability, which is how 34 secrets "survived" a teardown unreadable on 2026-09-01. The full restore rehearsal is the daily exit test for blocker 3, never a per-teardown step.
_Avoid_: backup check, smoke, teardown-verify (that is the post-destroy cost gate, a different thing)

**RPO** (recovery point objective):
The acceptable customer-data-loss window on an *unplanned* environment loss. A planned teardown takes a backup first (~0 RPO); the window only applies to a crash between scheduled backups. Cadence is unresolved (see open questions).

**Teardown-verify**:
A post-destroy gate that answers "did this env actually reach ~$0" by querying **what is in the sub-account**, not what Terraform thinks it created — because the costly survivors (NLBs/target groups from the AWS LB Controller, EC2 from Karpenter, EBS from the CSI driver, NAT gateways, EIPs) are **controller-created at runtime, outside Terraform state**, so a state-based sweep structurally can't catch them. Mechanism: Terraform `default_tags{Environment=<env>}` + a Resource Groups Tagging API scan + a direct sweep of the always-expensive untaggable classes. It has no second tool behind it. It fails red on a survivor. The permanent workspaces are exempt by service and by name, never by a tag. See ADR-0070.
_Avoid_: orphan cleanup (that's the brittle state-based predecessor), cost alarm (Budgets is reactive defense-in-depth, not this gate)

**Umbrella chart**:
The single self-contained Helm chart that *is* the product — CRDs→operators→workloads as ordered dependencies plus the (formerly gitops-only) ExternalSecrets, bringup Jobs, and CNPG cluster folded in and gated by values. It is the one artifact every consumer installs (helm / Argo / Flux). **Controller-agnostic from day one** (see ADR-0071): no Argo, Flux or Istio dependency is assumed, and federal, on-prem and air-gapped installs use the same chart with the air-gap image list in `charts:airgap/`. _Exists_ as `helm/gibson` (grill 2026-08-24 Q1): operators, workloads, neo4j, openfga, zitadel, spire and cnpg are its ordered dependencies. `gibson-crds` stays a sibling chart only because Helm cannot install a CRD and its CR in one release. **There is only ever one releasable, `gibson`.** The edge (Envoy, WAF, rate limiting, client-IP trust) is part of it, in `gibson-workloads`, for every audience and every substrate.
_Avoid_: app-of-apps (that's an Argo deployment of the chart, not the chart), the gibson chart (it's an umbrella of sub-charts), helm-gibson-install / "the installer" (a second name for the same artifact; there is no separate installer)

**GitOps tool**:
A swappable *consumer* of the umbrella chart (Argo for our hosted fleet; the customer's own Argo or Flux for an on-prem or air-gapped install; plain `helm`/`helmfile` for self-host and ephemeral envs) — never assumed by the chart and never the deployable unit itself.
_Avoid_: "the GitOps repo is the product"

**Lifecycle trigger**:
The destroy→recreate→restore→smoke run is **manually triggered** (`workflow_dispatch`) for both staging and prod for now, structured so a `schedule:` trigger is a one-line addition once teardown-verify is reliably green. App-plane promotion is separate (a branch-merge that Argo pulls).
_Avoid_: nightly (not yet — manual until trusted)

**Deployment audience**:
*Who* runs the platform — orthogonal to **Environment** (which is *which of ZeroRoot's own targets*). Two audiences:
- **Self-hosted** (a.k.a. on-prem): a customer runs it in their own infra (VPC / datacentre / air-gapped enclave). A strict **subset** — the self-hostable core with every **SaaS-only component** absent. Installed as the **umbrella chart** with the `self-hosted` profile (plain helm/helmfile, per **GitOps tool**).
- **SaaS**: ZeroRoot Cloud (`zeroroot.ai`), the superset — self-hosted core **plus** SaaS-only components and the public web surfaces. ZeroRoot's SaaS still has its own dev/staging/prod **Environments**.
_Avoid_: "on-prem build" (it's the same artifacts, a smaller profile — not a separate build), "the customer cluster" (name self-hosted)

**Core component**:
Present in **both** audiences — the self-hostable platform: daemon, the dashboard *app*, ext-authz, the operators, the data planes, and the Apache build/execute components (sdk/adk/setec/gibson-executor).

**SaaS-only component**:
Present only in the SaaS audience; **absent** self-hosted. Attaches to the core through a **seam**. Resolved seam catalog:
- **Entitlements/billing** [done, ADR-0060] — seam `ENTITLEMENTS_ENDPOINT`; fail-safe = OSS `ConfigProvider`.
- **Self-serve signup** [grill Q2] — the card-first signup surface (dashboard signup pages + Stripe SetupIntent + `SignupService`/`TenantProvisioningService` wiring) is SaaS-only. Fail-safe self-hosted default = the existing `TenantAdminService.AdminProvisionTenant` admin path (admin provisions tenants; no public sign-up — the GitLab self-managed model). Self-hosted **bootstrap**: a seed step (helm post-install hook / `gibson-cli bootstrap-admin`) creates the first admin + tenant from install-time config; not a stripped-down signup form.

**Profile ladder**:
The five named profiles, each layering on the one before it (ADR-0090):
`baseline < developer < CI < staging < production`. `baseline` is the
substrate-neutral floor a customer installs on a plain Kubernetes cluster.
`developer` is that floor sized to fit one local node, for kind and for k3d.
`CI` ships the same content as `developer`, under its own name so either may
change later without a rename. `staging` and `production` are this repo's
environments, and their values live in `gitops/envs/<env>/` rather than in the
chart. A rung lowers CPU and memory *requests*, never limits. It replaces the
name `vanilla`, which had come to mean five different things.
_Avoid_: vanilla, the self-hosted profile, the small profile

**Substrate** [grill 2026-08-24 Q3=accepted]:
The cluster's provider. A third axis, orthogonal to **Environment** (which of ZeroRoot's targets) and **Deployment audience** (who runs it). Values: `eks`, selected by the one **substrate overlay** `helm/gibson/values-eks.yaml`. The GKE and AKS overlays left the chart (D36, hosted#432): a cloud returns with its own stage 1 root and its own proof. The overlay is layered on a rung of the **profile ladder**. A plain Kubernetes cluster (k3d, OpenShift, Rancher, bare metal) needs no overlay: it runs the `baseline` rung alone. kind needs no overlay either, and it runs the `developer` rung by default or the `ci` rung, because the baseline alone has no mail sink (charts#503). The substrate is orthogonal to the ladder and is not a rung on it (ADR-0090) — a cluster is both `production` and `eks`. An overlay may carry only what that provider's controllers read: (1) Envoy Service annotations for load-balancer provisioning, client-IP preservation and health check; (2) `externalTrafficPolicy` for passthrough providers; (3) StorageClass and workload identity (the EKS overlay binds no IRSA role since deploy#1744), and NOT a secret backend (OpenBao is the one External Secrets backend on every substrate, deploy#1733) and NOT a cloud KMS key (deploy#1744); and, found while moving the EKS overlay (deploy#1656), (4) the provider region and the DNS-01 solver for the edge certificate, because both name a provider API. Nothing else, enforced by `scripts/check-substrate-overlay-allowlist.py`. A render guard in chart CI diffs the Envoy ConfigMap across all substrates and fails on any byte of difference, so the edge is provably one config everywhere [grill Q7].
_Consequence_: `ci/values-self-hosted-eks.yaml` moves to `helm/gibson/values-eks.yaml`. It is a deployment source, and a `ci/` path said otherwise.
**Proof level** [grill Q8=B]: every substrate overlay's header carries one line, `Proof: rendered in CI, not yet installed on a cluster`, or the link to the first green run of `exit-test-substrate.yml`. That workflow installs the umbrella with the named overlay on a real cluster (`workflow_dispatch`, substrate name + kubeconfig secret), waits for the Envoy Service's external address, and runs the blocker 4 assertion against it from two source addresses. It is the one exit test that needs a cluster, so it never runs on schedule. An overlay with no proof line is a defect (ADR-0090).
_Avoid_: "supported" for an overlay whose proof line still says rendered
_Avoid_: cloud (too broad, the marketing site is also "cloud"), platform (taken by the product), "the EKS profile" (a profile selects an audience, a substrate selects a provider)

**Edge WAF** [grill 2026-08-24 Q4=accepted]:
Coraza (Apache 2, OWASP Core Rule Set) running as a WASM filter inside the edge Envoy. A core, always-on component: no new deployable, runs on every substrate and in kind, one config everywhere. One filter, two rule profiles: the browser chain inspects request bodies at paranoia level 1, because it carries the pre-auth forms (signup, OIDC login, password reset); the `api.` chain runs with request-body access off, ahead of `jwt_authn`, so scanners are blocked and logged whether or not they hold a token. Its content-type allowlist admits `application/grpc`, `application/connect+proto` and `application/proto`.
A WAF inspects content for attack patterns. It is not admission control: a flood of well-formed requests passes it, and that is the **Edge rate limit**'s job. Tuning is by anomaly threshold, never a detection-only switch (ADR-0027). Proof is `exit-test-waf.yml` [grill Q7] on the same edge harness: a scanner-shaped request gets 403 on both chains, and a legitimate signup POST and a legitimate `application/grpc` call get through, so the WAF cannot pass by blocking everything.
**Filter order** on the browser chain [deploy#1658]: fuse (`local_ratelimit`) → per-client quota (`ratelimit`) → WAF (`wasm`) → router. A flood pays the cheap fuse and the quota before it pays CRS inspection, and a scanner's blocked requests still burn its quota. Envoy's validate mode instantiates the module, so every `envoy --mode validate` (CI bats, the harness) mounts the module from the pinned image (`tests/lib/envoy-wasm-module.bash`).
**Distribution** [grill Q11=B]: the `coraza-proxy-wasm` OCI image is mirrored to `ghcr.io/zeroroot-ai/mirror/`, digest-pinned by `digest-pin-check`, and an init container copies the module into an `emptyDir` that Envoy loads as a local file, so air-gapped installs work. The Core Rule Set version is that image digest. Directives live in `files/coraza/browser.conf` and `files/coraza/api.conf`. Every rule exclusion names the route and the fixture that showed the false positive, and there is no wildcard exclusion. Audit log to stdout, into the chart's Loki pipeline.
_Rejected_: a cloud WAF per substrate (needs an L7 load balancer, so a second edge, and no kind or self-hosted coverage); Coraza behind `ext_proc` (a hop for nothing the in-process filter lacks).
_Avoid_: "the WAF" meaning AWS WAFv2 (that ACL fronts the ArgoCD ALB only), DDoS protection (that is the substrate's L4 job, free on every provider)

**Edge rate limit** [grill 2026-08-24 Q5=accepted]:
Two layers on both edge chains, and both are core, always-on. (1) The **fuse**: the existing Envoy `local_ratelimit` buckets, absolute per route, per pod, unchanged. (2) The **per-client limit**: `envoyproxy/ratelimit` (Apache 2) as a Deployment in `gibson-workloads`, counting in the structural `gibson-redis-stack`, called through `envoy.filters.http.ratelimit` with `failure_mode_deny: false`. When the service is unreachable, traffic passes under the fuse and a metric fires (observable degradation).
Keys: pre-auth routes on both chains key on the client address from the **Client-IP contract**, masked /32 for IPv4 and /64 for IPv6. Authenticated `api.` routes key on JWT subject plus tenant from the `jwt_authn` payload, so one bad component throttles itself, not its customer.
**Quotas** [grill Q9]: fixed windows, no burst. Sizing rule: about ten times a real client's peak, always below that route's fuse, asserted by bats. Browser chain, by address: `POST /signup` 5/min; OIDC login (`/ui/login/`, `/oauth/`, `/oidc/`, `/device`) 30/min, and password reset and invite acceptance live under `/ui/login/` (Zitadel) so they share that quota [deploy#1659, the separate 5/min row had no route of its own]; everything else on `app.` 600/min. `api.` by address: `/capabilitygrant/v1/register` 10/min; `/.well-known/*` 120/min. `api.` authenticated `/gibson.*` by (tenant, subject) as ext-authz asserts them in `x-gibson-identity-tenant` / `-subject` (headers_to_set, ADR-0009), so the quota runs AFTER `ext_authz`: 50/s. All numbers live in `envoy.rateLimit` next to the fuse they sit under. Zitadel lockout stays as the layer behind the login quota.
**Wiring** [grill Q10]: Envoy reaches the ratelimit service over SPIFFE mTLS with its own `ClusterSPIFFEID`, the same SDS pattern as the daemon and dashboard upstreams. The ratelimit binary loads static certificate files only, so an Envoy sidecar in its pod terminates that mTLS through SDS (rotation-safe, client SAN pinned to `platform/envoy`) and forwards to ratelimit on loopback [deploy#1657]. A 429 from the quota carries `x-envoy-ratelimited: true`; `retry-after` is the fuse's header. Network policy allows exactly Envoy → ratelimit (gRPC) and ratelimit → `gibson-redis-stack:6379`, asserted by bats. Counters live under the `rl:` key prefix in the one Redis Stack, no logical database. Ratelimit replicas follow Envoy's replica count in every overlay.
This is blocker 4's exit test, `exit-test-rate-limit.yml` [grill Q7]: client A exhausts the signup limit and gets 429 while client B gets 200, and the same on `api.` with two JWT subjects, run offline on the shared **edge harness** (rendered chart → Docker Envoy, ratelimit and Redis, two client containers so the peer address is real).
_Rejected_: `local_ratelimit` descriptors alone (per-pod counters double the limit at `replicas: 2` and split one client across pods); `local_cluster_rate_limit` (divides the total, still per pod); a cloud WAF rate rule (needs an L7 edge, and no kind or self-hosted coverage).
_Avoid_: "the rate limit" without saying fuse or per-client, throttle (the fuse is a ceiling, the per-client limit is a quota)

**Client-IP contract** [grill 2026-08-24 Q2=accepted]:
Every substrate's L4 load balancer delivers the client's source address as the TCP peer Envoy sees. Envoy trusts the socket peer only (`use_remote_address: true`, `xff_num_trusted_hops: 0`), never a client-supplied `X-Forwarded-For`. A substrate that cannot preserve the client IP is not a supported substrate. This is what makes a per-client rate limit and a WAF rule keyed on address real rather than spoofable.
Per substrate: AWS NLB `preserve_client_ip.enabled=true` with the NLB's own security group carrying the public rule; kind and the baseline profile use `externalTrafficPolicy: Local`. Hairpin is avoided because every in-cluster client dials the fixed ClusterIP through a hostAlias, never the public hostname.
_Rejected_: PROXY protocol v2 (AWS-only, so it can never be the one design); an ALB or CloudFront inserting `X-Forwarded-For` (a second edge, `api.` left uncovered, see deploy#1196); `xff_num_trusted_hops: 1` (only correct behind an ALB).
_Reverses_ deploy#1196 option B (owner call 2026-08-24, grill Q6): the split edge is retired by a surgical `fix(rework):` PR that deletes the `alb_ingress` listener, the ALB Ingress and Service, `envoy-alb-edge.bats`, the `albEdge` values and `module "wafv2_edge"`. `public-chain.yaml`, the one-record-per-host rule in `service.yaml` and the bats hardening from deploy#1609 stay. One edge, one listener, SNI-selected chains, on every substrate.
_Avoid_: "real IP header", "trusted XFF" (there is no trusted header, only the peer)

**Bootstrap (self-hosted)**:
The first-admin/first-tenant seed on a fresh self-hosted install, since there is no self-serve signup to create the initial principal. A bringup hook/CLI step from install-time config (cf. GitLab's initial `root` admin).

**Seam**:
The interface where a **SaaS-only component** attaches to the core, carrying a **defined fail-safe self-hosted default** that takes over when the component is absent. Proven template: entitlements (ADR-0060) — `ENTITLEMENTS_ENDPOINT` unset → OSS `ConfigProvider`; set → the closed Stripe service. The rule: *off = absent = degrade to the free/open behavior* (the safe failure direction).
_Avoid_: feature flag (a seam is component presence/absence per profile, not a runtime flag in one image), license gate

**Deployment profile**:
The Helm values set selecting which components are present: `self-hosted` (core only) vs `saas` (superset). The **toggle mechanism** is deployment-profile + fail-safe seam, **not** a runtime license-key gate. [grill 2026-06-29 Q1=A]

**SaaS overlay**:
The packaging of all SaaS-only components as **separate charts/Argo apps layered on top of** the core umbrella — NOT folded into it. The **core umbrella carries only the seam knobs** (e.g. the daemon's `ENTITLEMENTS_ENDPOINT`, unset by default) and **zero closed/SaaS image references**; the overlay supplies the SaaS-only deployables (billing/entitlements-svc, marketing, signup enablement, fleet) and **sets the seam knobs** (points the core at them). Self-hosted installs the core umbrella alone. GitLab model: the self-managed chart contains no `.com`-only services. [grill Q5 → chose separate-overlay over gated-within]
_Consequence_: the entitlements-svc shipped in deploy#1002 (currently inside `gibson-workloads`, gated by `entitlementsSvc.enabled`, referencing `ghcr.io/zeroroot-ai/billing`) must **re-home into the SaaS overlay**, leaving only the daemon's `ENTITLEMENTS_ENDPOINT` knob in the core.
_Avoid_: "saas umbrella" (it's a composition in ZeroRoot's private gitops, not a second shipped chart), gated-within

**Component taxonomy** (four shapes) [grill Q4; fourth shape added 2026-08-18]:
- **SaaS-only** — absent self-hosted, but still deployed by a chart in the **SaaS overlay**: billing/entitlements, self-serve signup.
- **Off-cluster surface** — deployed by *no* chart in *either* audience: the **marketing site**. See below.
- **Core, always-on** — both audiences: daemon, dashboard *app*, ext-authz, operators, data planes, sdk/adk/setec/gibson-executor.
- **Core, optional-by-toggle** — ships self-hosted, default-on, may be disabled with a fail-safe: **docs** (own repo #819, Apache/Fumadocs; **one versioned deployable, two consumers** — see below; **version-matched to the installed platform** for air-gapped; online self-hosted may toggle the local docs off and link to public `docs.zeroroot.ai`).

**Docs: one deployable, two consumers** [grill 2026-08-18 Q2=A]:
The docs deployable is the **static export** of `docs-site` at a **release tag**. Two consumers publish it, and both are cut from that same commit:
- the **container image** (nginx), pinned by digest in the umbrella chart — the self-hosted and air-gapped copy;
- the **public publish** to object storage behind a CDN at `docs.zeroroot.ai` — an **off-cluster** delivery of the same export.
Neither consumer is a parallel codepath under ADR-0027: same source, same tag, same bytes. Publishing the public copy from `main` instead would break that, because the public site would then lead every release.
_Avoid_: "the docs image is the artifact" (it is one consumer of it), publishing public docs from `main`

**Off-cluster surface** [grill 2026-08-18 Q1=A]:
A public web surface that **no chart deploys in either audience**. It is built from its own repo, published to object storage behind a CDN, and reached only through DNS — so it has no Deployment, no Service, no Envoy virtual host, and therefore **no seam and no fail-safe**, because there is nothing present to degrade. Distinguished from a **SaaS-only component**, which is absent self-hosted but still a chart in the **SaaS overlay**.
Current members: the **marketing site** (`www.zeroroot.ai`), and the public consumer of the **docs** deployable (`docs.zeroroot.ai`).
Provisioned by its own singleton root, `eks/public-site` — **the one root in this repo with no Environment** (see below). Deliberately NOT in `eks/gibson`: that root is full-ephemeral (ADR-0083), so the site would be destroyed on every teardown.
Its bucket and distribution are permanent residents of the workload account. **teardown-verify** recognizes them by service (CloudFront, S3, ACM) and by the `www-*` name of the lead path, never by a tag: the `teardown:keep` allowlist was deleted with the retain machinery (deploy#1743).
_Done_ (deploy#1622): `helm/saas-overlay/www-svc`, the `www` virtual host and the `gibson_www_svc` STRICT_DNS cluster (with its 503 fail-safe) are deleted, and `www` is out of `gibson.externalDnsHosts` — that last line is the one that decided whether a cluster claims the hostname. The edge split (deploy#1196) narrows to `app` + apex, and the apex now redirects to `app.<domain>`, since it cannot send a self-hosted visitor to a marketing site that does not exist there.
_Live_: both surfaces are serving from `eks/public-site` (applied 2026-08-18). `www.zeroroot.ai`, `zeroroot.ai` (301 → www) and `docs.zeroroot.ai` answer; `/api/contact-sales` is a second origin on the www distribution.
_Avoid_: "SaaS-only component" (that shape is chart-deployed), "static site" (says how it is built, not who deploys it), "unrouted" (the old fail-safe, now moot — the vhost is gone, not empty)

**Lead path** [grill 2026-08-18 Q5=A]:
How a contact-sales submission reaches a human, with no dashboard running. A Lambda Function URL is a **second origin on the `www` distribution** at `/api/contact-sales`; the Lambda publishes to an SNS topic that emails the sales inbox.
Same-origin **by construction**, which is the point: the dashboard's `/api/contact-sales` needed an origin allowlist, an `OPTIONS` preflight, `Vary: Origin` and a 403-on-unknown-origin branch **only** because the form and the API sat on different hosts. None of that is ported — it is deleted. `APP_ORIGIN` leaves `ContactSalesForm.tsx`.
SNS, not SES: no domain identity and no production-access request, and it keeps lead mail off the signup verification sender's reputation (blocker 2). Trade-off accepted: SNS mail is plain text from an Amazon address, so the lead's address is in the body and reply-to does not work.
Rate limiting is the **account's Lambda concurrency ceiling** (currently 10), not WAF — a WAF rate rule costs ~$6/mo against a ~$2/mo site. A per-function reservation is impossible here anyway: AWS refuses any reservation that drops unreserved concurrency below 10, and the account total *is* 10.
_Built as_ an HTTP API, not a Lambda Function URL. With `AWS_IAM` + CloudFront OAC the caller must sign the payload, which CloudFront cannot do for a request with a body (hashing it at the edge needs Lambda@Edge — CloudFront Functions cannot read the body); with `NONE` auth a `Principal: "*"` resource policy is not honoured in this account. Both failed invisibly, because the distribution's 403→404 mapping fetched the error page from the S3 origin and surfaced an unrelated S3 `AccessDenied`.
_Avoid_: cross-origin contact form (the shape we are deleting), SES for leads

**Seam convention** [grill Q6]:
The formalized, enforced contract every **seam** must satisfy — so "toggle on/off and it works" is a *proven* property, not per-seam luck:
1. **Declaration** — a config knob on the core (env/values) where unset/empty = the fail-safe self-hosted default; every seam listed in the **seam registry** (the catalog above + the ADR table: knob → fail-safe → the SaaS component that fills it).
2. **Fail-safe test** — every seam ships a unit test proving *knob unset → free/open behavior runs* (generalizing `entitlements.TestNew_DefaultsToConfigProvider`).
3. **No-closed-refs render guard** — CI asserts the core umbrella rendered with the `self-hosted` profile contains **zero** closed/SaaS image references (same shape as the no-committed-`.tgz` guard, deploy#1001) — mechanically enforcing the **SaaS overlay** separation.
4. **Observable degradation** — every fail-safe *activation* emits a metric/log, and the core logs its resolved seam state (wired vs fail-safe) at startup, so a SaaS deployment silently running a seam degraded (e.g. entitlements unreachable → unlimited) is detectable/alertable. Fail-open is safe *and* visible.
_Avoid_: ad-hoc seam, "it'll fail open" (must be tested + observable, not assumed)

## Relationships

- An **Environment** is provisioned by the **infra plane**, then populated by the **app plane**.
- **Promotion** moves config between environments; it does not move data.
- A **teardown** in either mode is the inverse of a **recreate**. Only a **preserve teardown** produces a backup name, and only a named backup makes a recreate restore ([ADR-0083]).
- The **substrate bootstrap** outlives every teardown. **Preflight** stands between it and a recreate. The **bringup keyring** is what makes the **durable bucket** readable, and **backup-verify** proves that with the same keyring before a destroy.
- The **backup cadence** covers unplanned loss. A **preserve teardown** covers planned loss. Neither replaces the other.
- The same **recreate** path is simultaneously the deployment-mechanism regression test and the DR/restore test.

## Flagged ambiguities

- "preserve" used to mean *some AWS resources survive the destroy* (`prevent_destroy`, `state rm`, `teardown:keep`, EBS-volume capture) — the retain-and-reimport model [ADR-0083] rejected. Resolved 2026-09-01: **preserve means export**. A **preserve teardown** backs up to the **durable bucket** and then destroys everything, exactly like a **wipe teardown**. Nothing is carved out of the blast radius. The retain machinery was deleted, not maintained (deploy#1743), and `scripts/check-no-retain.py` fails the build on any of those constructs under either stage 1 root.

- "prod" the AWS *sub-account* (`zeroroot-ai-prod`) vs "prod" the *environment* — the cheap standup cluster lives in the prod sub-account but is not the prod environment. Name the environment, not the account.
- "deleted fast / recreated fast" initially read as ambiguous between cluster-only and everything — resolved to **everything** (full-ephemeral) for both staging and prod ([ADR-0083]).
